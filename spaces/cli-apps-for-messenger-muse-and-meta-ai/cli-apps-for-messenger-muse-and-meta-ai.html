Command-line versions of Messenger, Muse, and Meta AI — what actually exists

Short answer: there is no official CLI for Messenger, for the Muse personal agent, or for Meta AI — but the idea behind the question works. An agent on Ubuntu can talk to other agents from the terminal, through three real doors: Muse Code's session messaging (one agent session messaging a peer session on the same machine), the Muse Gadgets SDK (musegadget send-user-msg — the only Meta-published CLI that delivers a message into the Muse personal agent), and the open MCP and A2A protocols. Messenger from the terminal is sanctioned only as a Facebook Page, never as a personal profile.

Page API only · personal = unofficial
1 · Facebook Messenger

No official CLI and no official Linux app at all. The sanctioned terminal route is the Graph API acting as a Page you administer. Personal-account CLIs exist but are mostly abandoned; the one maintained route (mautrix-meta) logs in with browser cookies and carries account-block risk.

No CLI — but an official gadget bridge
2 · Muse (personal agent)

No CLI and no public API for Muse itself; official clients are iOS, Android, Mac, web, and WhatsApp. The exception: Meta's open-source Muse Gadgets Linux SDK turns an Ubuntu box into a Muse-controlled device whose local programs can message Muse from the shell.

Nothing official
3 · Meta AI in Messenger

No CLI and no consumer API for the in-Messenger assistant, and no way to script your personal conversation with it. The sanctioned developer substitute is the Meta Model API — the same model family, a different product, with no access to your Messenger thread or Meta AI's memory.

First, the naming trap: four different things

Most confusion — and most misleading "muse cli install" search results — comes from four products sharing names. Keep these separate and every verdict below makes sense.

THING 1

Muse — the personal agent

Meta's consumer personal AI agent, launched 2026-09-08. App, muse.ai, and WhatsApp. This is the "Muse" the question is about — and it has no CLI.

THING 2

Muse Code — the terminal coding agent

A separate developer product. Its binary is literally named muse, it is a real official CLI for Linux, and it produces most "muse cli" search hits. It is not a CLI for the personal agent.

THING 3

Meta AI — the assistant in Messenger

The blue-circle assistant inside Messenger, Facebook, Instagram, and WhatsApp (invoked as @Meta AI in group chats), plus meta.ai and the Meta AI app.

THING 4

Meta Model API — the models, as an API

A developer API serving the Muse models (Muse Spark / Muse Wonder). An endpoint into the models — not into the Muse personal agent, and not into your Meta AI session.

1 · Facebook Messenger

Verdict: no official CLI, on any OS. Meta offers no messenger command-line tool and no official Messenger desktop app for Linux at all. Meta discontinued even its Windows and macOS desktop apps on 2025-12-15, redirecting users to the web at facebook.com/messages / messenger.com.

The official route: Messenger Platform on the Graph API — Page-only

To integrate with Messenger officially you create a Meta app (Business type) at developers.facebook.com, add the Messenger product, connect a Facebook Page you administer, generate a Page access token with the pages_messaging permission, register a publicly reachable HTTPS webhook subscribed to messages / messaging_postbacks, and reply through the Send API. In Development mode only people with a role on the app can message it; public use requires App Review (and, for advanced access, Business Verification). Free-form replies are constrained by the 24-hour messaging window, message tags and Human Agent exceptions aside.

Personal accounts: no

"Messenger integrations always run through a Facebook Page, never through a personal profile. Users message the Page, Meta delivers those events to your webhook, and your app answers as the Page." There has been no sanctioned personal-profile chat API since Meta shut off the old XMPP chat API in 2015. A personal account's role is limited to administering the app/Page and messaging the Page as a user.

The closest thing to an "official CLI" for Messenger is calling the Graph API from a terminal — as the Page:

# Send as your Page (Page access token required)
curl https://graph.facebook.com/v26.0/{page-id}/messages …

# Official SDKs (libraries, not CLIs — both run on Ubuntu)
pip install facebook-business        # Python
npm install facebook-nodejs-business-sdk   # Node

Graph API versioning in 2026: v25.0 (Feb 2026) / v26.0 (Jul 2026), each supported ~2 years — pin a version. Meta's three official remote MCP servers (Ads, Meta Social Technologies / DevTools, WhatsApp Business Tools) do not cover Messenger-personal or Page organic messaging. Meta did launch a real Ads CLI alongside the Ads MCP in April 2026 (Python 3.12+, system-user token) — official, but for ad accounts, not Messenger.

2 · Muse — the personal AI agent

Verdict: no official CLI and no public API — but an official Linux gadget SDK gives a real CLI bridge. Muse launched 2026-09-08 as "a secure, private personal AI agent" running on a dedicated cloud computer (the Muse Secure VM, with a separate Sentinel agent approving anything that reaches the internet), powered by Muse Spark. It sends email, books, fills forms, buys (Link by Stripe), remembers preferences, and keeps working after the app closes, asking approval before sensitive actions. Official surfaces at launch: iOS, Android, and muse.ai, "coming soon to AI glasses", plus messaging it in WhatsApp. Free tier plus subscription plans.

  • No public API for driving Muse. Independent probes found muse.ai/llms.txt returns 401 behind auth, with no public API spec, no MCP discovery surface, and no documented headless/CLI/CI mode. A DigitalOcean comparison (updated 2026-10-28) agrees: "Developer API for the agent: None documented… none documents an API for creating or messaging the agent itself."
  • The asymmetry matters: Muse itself can reach out — built-in connectors (Gmail, Calendar, Instagram, Facebook, etc.), Custom Connectors it writes for services that "have their own APIs or CLIs", and connector submissions via the Muse Connector Platform. That is Muse calling other tools — not a way for your program to call Muse.
  • Sign-in: a Meta (Facebook/Instagram) account at muse.ai or in the app; availability began in the US (later US+Canada and further rollouts reported), 18+. There is no developer-account or API-key route into the personal agent. A Meta Model API key buys the Muse models, not the Muse agent — different product, no shared memory, tasks, or connectors.
  • Ubuntu: the official desktop app is Mac only (checked Oct 2026 — no Windows, no Linux). On Ubuntu the official route is the web app at muse.ai in a browser, with the full agent, since the work happens on Muse's cloud VM. No apt/PPA/Snap/Flatpak/vendor .deb from Meta. An unofficial Electron wrapper, benjaminkitt/muse-desktop, offers a Linux .deb/AppImage — a GUI wrapper of muse.ai, unsigned, not Meta's, and not a CLI. (Also beware registry collisions: unrelated projects named "Muse", e.g. an audio-to-MIDI app with Ubuntu .debs, are not Meta's Muse.)

The official bridge: Muse Gadgets (musegadget)

On 2026-10-02 Meta open-sourced Muse Gadgets (Apache-2.0, facebookincubator/muse-gadget-sdk): ESP32 firmware plus a Linux Device SDK for building devices that work with Muse. It works in both directions:

Muse → your Ubuntu box

A systemd service (musegadget, in /opt/musegadget) lets Muse call system.run (shell command, returns output + exit code), file.read / file.write (64 KB chunks), and device.health — as the account you installed for. "If it can use sudo, so can Muse." Add your own commands as JSON files in /etc/musegadget/commands.d/.

⇄
Your Ubuntu programs → Muse

"Programs on the machine can send messages to Muse, with no credentials of their own" — via musegadget send-user-msg, below. Use --session-id side chats for clean, attributable request/response instead of racing the main chat.

musegadget send-user-msg "The garage door has been open for an hour."
musegadget send-user-msg --session-id <uuid> "Posted to a side chat"
musegadget send-user-msg --image porch.jpg "Who is at the door?"
musegadget send-user-msg --wait 120 "…"   # waits 1–600s, prints Muse's answer; exit 3 on timeout

Requirements: Ubuntu 22.04+ (or Debian 11+ / Pi OS Bullseye+ / Arch / Fedora), Bluetooth LE (pairing only), Python 3.9+, an account with sudo, a phone with the Muse app, and an SDK token (mgst_…) from gadgets.muse.ai (Account → SDK tokens). Pairing: Muse app → Settings → Devices → Developer mode on → Add Device (MuseGadgetXXXXXX); the pairing window is 10 minutes (sudo musegadget pair reopens it).

# Official install — the README tells you to read the script first
curl -fsSL https://raw.githubusercontent.com/facebookincubator/muse-gadget-sdk/main/linux/install.sh -o install.sh
less install.sh
bash install.sh --sdk-token mgst_…

# Manage
sudo musegadget info | doctor | pair
sudo systemctl status musegadget
sudo journalctl -u musegadget -f

# Remove
bash install.sh --uninstall [--purge]
Limits & risks, in Meta's own framing

"Built by hackers, for hackers, just for fun." Community pairing "has no manufacturer verification and can't prevent an active man-in-the-middle attack" — pair on a trusted network. Token terms (per secondary summaries of gadgets.muse.ai/sdk-terms) restrict tokens to personal, non-commercial use, ≤50 devices per token, and state the SDK/tokens are not a supported product / not a developer platform and may change or be withdrawn. Security posture is on you: install --run-as a dedicated, non-sudo account unless you truly want Muse to have sudo.

Unofficial Muse bridges

Because Muse has no public API (its chat runs over an encrypted WebSocket, wss://hatch.metaaivm.com/v1/noise per the bridge authors), community bridges drive your logged-in Chrome:

  • Muse-Chat-MCP (duclm1x1 / fierzone forks; Glama-listed): an MCP server over stdio with tools muse_chat, muse_status, muse_login, muse_new_chat, muse_read_last, plus an OpenAI-compatible HTTP shim and a small muse-cli.mjs one-shot CLI. It types into the muse.ai composer via Playwright and reads the rendered reply; you sign in with your own Meta account in a dedicated Chrome profile. Explicitly "unofficial, unaffiliated." npm variant: @santaclone/muse-mcp (npx -y @santaclone/muse-mcp --login).
  • niclydon/muse-mcp: notable because it is built on the official gadget Link API rather than scraping — pair a Linux host as a Muse Link device, then an MCP server (39 tools) turns a Muse chat ID into an addressable endpoint any MCP client can message. The server is unofficial; the underlying SDK is Meta's.
  • Hosted resellers (e.g. useapi.net's Muse API / hosted MCP): third parties running on your Muse subscription via their infrastructure — highest trust cost; not affiliated with Meta.

These do not use a sanctioned API into Muse (none exists), so they can break when muse.ai changes, and browser-automation of a consumer account is outside the routes Meta documents for Muse. The gadget-SDK route above is the only one Meta itself published.

Muse Code — the other Muse, which is an official Ubuntu CLI

Meta's terminal coding agent (beta 2026-08-05, GA 2026-08-31), built for Muse Spark, positioned against Claude Code / Codex. One codebase runs on macOS, Linux, and Windows. There is no apt/PPA/Snap/Flatpak — the curl installer (or the SDK packages) is the distribution mechanism. The CLI is proprietary; the SDK/protocol are MIT.

curl -fsSL https://dev.meta.ai/install.sh | sh   # macOS/Linux; native `muse` binary on PATH (~/.local/bin)
muse --version
muse                  # interactive TUI in a project
muse exec "<prompt>"  # headless, one prompt to completion — for scripts/CI
  • Sign-in: first run shows a trust-the-workspace prompt, then browser sign-in or an API key; for CI/headless set META_API_KEY. Billing: a Muse Code subscription plan or pay-as-you-go Model API tokens. Default model per current docs: muse-spark-1.2 (1.3 available).
  • Programmatic drive: muse serve runs the Muse Session Protocol (MSP) — an open protocol over standard I/O (JSON-RPC, no server, no network); muse schema prints its schema. TypeScript: npm install @muse-code/sdk (Node ≥20, zero deps, Developer Preview); Python: pip install muse-code-sdk.
  • MCP client support: Muse Code connects to MCP servers declared in the mcp_servers block of ~/.config/muse/settings.json (transports stdio and streamable_http; muse mcp login/logout <server> for OAuth servers; /mcp in-session lists connected servers/tools). So a Muse Code session on Ubuntu can call tools — including community MCP servers that wrap the Page Graph API, or a Muse-Chat-MCP server — through a sanctioned extension point of Muse Code, even though the wrapped target may itself be unofficial.

3 · Meta AI in Messenger

Verdict: nothing official. There is no official CLI for Meta AI and no API into the consumer Meta AI assistant — in Messenger, in the app, or at meta.ai. Meta AI is a consumer surface only: Messenger/Facebook/Instagram/WhatsApp in-app, meta.ai web, the Meta AI app (iOS/Android at launch, built with Llama 4), and AI glasses. Its model has since changed — 2026 sources report Meta AI now running on the Muse Spark family in the app/meta.ai and rolling out to Messenger — but the access model has not: still no developer endpoint for "the assistant in your Messenger."

Either way, the CLI answer is still "none." This page treats the item as Meta AI in Messenger and flags the nickname as unverified.

  • You cannot message Meta AI in Messenger programmatically as yourself. The Messenger Platform lets a Page bot reply to users; it does not let you script your personal account's conversation with the Meta AI contact, and Meta AI is not a Page you can connect to your app.
  • Ubuntu: officially, nothing to install — no apt/PPA/Snap/Flatpak/.deb for Meta AI; a browser to meta.ai is the Ubuntu route.
  • Local alternative with Meta lineage: Llama open weights (Llama 4 family) can be self-hosted on Ubuntu (Ollama/vLLM etc.) — fully local, no Meta account, but again not "Meta AI in Messenger," and full-size models need substantial hardware.

The sanctioned substitute: Meta Model API

Hosted, self-serve (US developers in public preview at announcement), OpenAI-SDK-compatible (Chat Completions + Responses) and Anthropic-Messages-compatible. Base URL https://api.meta.ai/v1, key = MODEL_API_KEY from the dev.meta.ai dashboard, models muse-spark-1.1 → muse-spark-1.3 (and Muse Wonder via API per later docs). Any OpenAI-compatible agent CLI (e.g. OpenCode, which ships a built-in Meta provider) can be pointed at it. Meta's own help page stresses the distinctions: Model API ≠ Llama (download-and-host open weights) ≠ Llama Stack.

# From Ubuntu — no install beyond an SDK
pip install openai

# then in Python:
OpenAI(base_url="https://api.meta.ai/v1", api_key=os.environ["MODEL_API_KEY"])
# model: muse-spark-1.3

The same model family behind current Meta AI/Muse products, callable from Ubuntu with curl/Python/Node today.

  • metaai-sdk / mir-ashiq/metaai-api (PyPI/GitHub): "Unofficial Python SDK and API server for Meta AI… ⚠️ This is an unofficial, reverse-engineered client. Can an agent use a CLI to talk to itself?

Yes — but not by messaging itself in Messenger, and not through the Muse personal agent's (nonexistent) API. The legitimate architectures that exist today:

4.1 Muse Code session messaging — the literal feature

Start two or more interactive muse sessions on the same machine, same user account (macOS/Linux; unavailable on Windows), name them (/name api-review-482731), then in one session: "List my peer sessions, then send api-review-482731 this message: …". Delivery modes: steer active turn / queue for next turn / notify-only; the recipient can be woken when idle. Per Meta's GA blog: "Messages travel over a Unix socket between processes owned by you, so nothing crosses the network."

  • Hard limits, by design: plain text, ≤8,192 bytes; self-messaging is rejected (a session cannot message itself — peer sessions only); no cross-user or cross-machine transport; headless / --no-session-log sessions don't appear as peers.
  • Safety model worth copying: a peer message is unverified agent-provided data — it cannot approve a tool call, grant consent, or change permissions; the receiving session may prompt its user to allow/reject/block the sender (approvals expire in 30 min).
  • A CLI surface also exists in the binary (per third-party help dumps): muse session-message list --json, muse session-message send --target <session> … — treat the documented natural-language route as primary; the subcommand spelling is from community sources, not Meta's session-messaging page.

4.2 Driving an agent from your own program — muse serve / MSP, and muse exec

An Ubuntu agent (any language) can spawn and drive a Muse Code session: muse serve speaks MSP over stdio, wrapped by the official TS (@muse-code/sdk) and Python (muse-code-sdk) clients. Start session, send turns, handle approvals, stream results — all local, no network. Simpler still: muse exec "<prompt>" (headless, JSON output options) is the scriptable one-shot form any shell-driven agent can call, exactly like calling Claude Code or Codex headless. Inside one session, Muse Code also has subagents/workflows — self-delegation without any external protocol.

4.3 musegadget send-user-msg — a local program talks to Muse, the personal agent

After pairing an Ubuntu box as a Muse gadget (§2 above), any local process can run musegadget send-user-msg --wait … and get the personal agent's reply on stdout. This is currently the only Meta-published CLI that delivers a message into the Muse personal agent. Its shape: the Ubuntu box is Muse's device, the message arrives as a user message on that account, and replies on the main chat aren't labelled by source — use --session-id side chats for clean request/response. The reverse channel (Muse invoking system.run / custom commands on the box) makes the pair genuinely bidirectional.

4.4 MCP — agent → tools (not agent → agent, despite the common confusion)

The Model Context Protocol (open standard, now under the Linux Foundation's Agentic AI Foundation): an MCP client inside an agent host connects to MCP servers that expose tools/resources/prompts. Transports: stdio (client launches the server as a subprocess; JSON-RPC over stdin/stdout) and Streamable HTTP. On Ubuntu today you configure servers in the host — e.g. Muse Code's ~/.config/muse/settings.json mcp_servers block — filesystem/Git/database servers, community Page-Messenger MCP servers, a Muse-Chat-MCP server to reach the Muse personal agent, or Meta's official Ads/DevTools/WhatsApp MCP servers. MCP servers do not talk to each other; the host coordinates. So MCP lets an agent use Messenger-the-Page-API or Muse-the-web-app as a tool — it does not make two independent agents peers.

4.5 A2A — agent → agent (the protocol actually designed for this)

Agent2Agent (A2A), originated by Google and donated to the Linux Foundation (now AAIF alongside MCP), spec v1.0: agents publish an Agent Card (capabilities, endpoint, auth) at /.well-known/agent-card.json, then exchange Messages that create Tasks and return Artifacts, over JSON-RPC/gRPC/HTTP+JSON with streaming and push notifications. There is an official CLI: a2a from github.com/a2aproject/a2a-cli — "the official command-line client for discovering, messaging, and managing A2A agents from a terminal or script." An Ubuntu agent can message any A2A-speaking agent (built on LangGraph/CrewAI/ADK/…) — provided the other side implements A2A. Neither Muse, Muse Code, nor Meta AI exposes an A2A endpoint, so A2A does not reach Meta's agents; it is the right architecture for agent↔agent with non-Meta or self-built agents (wrap your own agent in an A2A server, or wrap a CLI like muse exec behind one).

4.6 Plain local IPC — always available, no AI protocol needed

Two agent processes on one Ubuntu box can always communicate via Unix domain sockets, named pipes, D-Bus (session bus at /run/user/<uid>/bus), files/worktrees, or a local HTTP server. This is exactly what the products above formalise (Muse session messaging = Unix socket; MSP/MCP stdio = stdin/stdout of a spawned subprocess). For a self-built multi-agent setup on Ubuntu, stdio-MCP for tools + A2A or a simple socket/HTTP bus for peers is the standard, legitimate pattern — no Meta account involved.

What does not work — explicit negatives
  • An agent cannot DM itself or another agent as a personal Messenger user through any official route — only as a Page, to users who messaged the Page, inside the 24h window.
  • An agent cannot invoke the Muse personal agent via API/CLI from another machine — only via a paired gadget on that Muse account, WhatsApp chat with Muse (a human-style surface with no programmatic personal-account route), or unofficial Chrome-driving bridges.
  • An agent cannot invoke Meta AI in Messenger programmatically at all; the Model API is a model endpoint, not that assistant.
  • Muse Code session messaging cannot cross machines/users and cannot self-message — for cross-machine agent talk, use A2A/MCP-over-HTTP or your own bus.

What an Ubuntu agent can actually use today

  1. Run a Meta coding agent in the terminal

    Install Muse Code — curl -fsSL https://dev.meta.ai/install.sh | sh — sign in in the browser or set META_API_KEY; use muse interactively and muse exec "…" in scripts. OFFICIAL · §Muse Code

  2. Talk agent-to-agent with itself, same box

    Run two named Muse Code sessions and use session messaging; or drive sessions programmatically via muse serve + @muse-code/sdk / muse-code-sdk. OFFICIAL · §4.1–4.2

  3. Exchange messages with the Muse personal agent

    Pair the Ubuntu box with the Muse Gadgets Linux SDK (SDK token from gadgets.muse.ai, BLE pairing via the phone app), then musegadget send-user-msg --session-id <uuid> --wait 120 "…" from any local process; optionally expose custom commands to Muse in /etc/musegadget/commands.d/. Install --run-as a limited account. OFFICIAL SDK, "FOR FUN"/UNSUPPORTED TERMS · §2

  4. Get Muse-model answers from code or another CLI

    Meta Model API — https://api.meta.ai/v1, MODEL_API_KEY, model muse-spark-1.3, via the OpenAI/Anthropic SDKs or any OpenAI-compatible agent CLI (OpenCode has a built-in Meta provider). Substitutes for "Meta AI" for most automation, without pretending to be the Messenger assistant. OFFICIAL · §3

  5. Do Messenger from the terminal, sanctioned

    Be a Page: create the Meta app + Page, get a Page token (pages_messaging), receive webhooks, reply with Graph API calls (curl / pip install facebook-business). Optionally front it with a community Page MCP server for MCP-speaking agents. OFFICIAL API, PAGE-ONLY · §1

  6. Do personal Messenger from the terminal

    Only unofficial options. The maintained one is mautrix-meta into a Matrix client (cookie login; expect possible Meta suspicious-activity blocks). The historic CLIs (Messer, fb-messenger-cli, fbchat, bitlbee-facebook) are unmaintained/inactive. New cookie-copying "for LLMs" CLIs (e.g. fb) are unproven and carry the highest account risk. UNOFFICIAL · §1 — use a throwaway/secondary account if ever tested, and expect breakage

  7. General agent↔agent beyond Meta

    A2A (the a2a CLI + Agent Cards) for peers, MCP (stdio/HTTP) for tools — both run natively on Ubuntu and neither needs a Meta account. OPEN STANDARDS · §4.4–4.5
